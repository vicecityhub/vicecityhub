# ADR-0006: One persistent shell, pages swapped in place

- Status: accepted
- Date: 2026-11-22
- Deciders: Ser (owner), Claude

## Context
Every section of the site is its own HTML entry (a multi-page Vite app plus the generated static SEO pages), so a click on a menu link loaded a NEW document. The `<audio>` element of Leonida FM died with the old document and a new one was created on the next page. Desktop Chrome often carries a user activation across same-origin navigations, but iOS Safari and strict WebViews do not: the new element needs its own touch, so on a phone the music went silent after every section change and came back (restarted, or as another track) only after the next tap. Remembering the track and the position across page loads (`radioTracks`, `radioTrackIndex`, `radioTime`) hides the restart, but it cannot remove the silence. The only real fix is to never create a second document.

## Decision
- **One shell script on every page.** `public/vch-shell.js` is built from `src/shell/` by `scripts/build-shell.mjs` (esbuild, classic IIFE, no imports) and loaded by every page: React pages through `vite-plugins/vch-shell.ts` (end of `<body>`), generated static pages through `shellTag()` in `scripts/lib/seo.mjs` (before their inline script). The reference carries a content hash, `vch-shell.js?v=<sha1 slice>` (`scripts/lib/shell-ref.mjs`), because the file itself is not fingerprinted and GitHub Pages caches it. `reset-password.html` has no shell on purpose (always a plain page load).
- **The shell owns the radio.** `src/shell/radio.ts` creates the single `<audio>` of the document and keeps it for its whole life. Playback is retried at load and on EVERY user gesture (`click`, `keydown`, `touchstart`, `touchend`, capture phase) while the radio should play but is paused; the end of a track picks a random different track on the same element without any gesture. The playlist is the listing of the public `muz` bucket (`src/shell/playlist.ts`, needs the `muz_public_read` policy) and is remembered in `localStorage`. Mute is per browser session (`sessionStorage.radioPlaying`).
- **The shell owns navigation.** `src/shell/softNav.ts` intercepts clicks on links to other pages of the site (`src/shell/navRules.ts` decides which) and back/forward, fetches the target page, and swaps `<head>` (only the elements that belong to a page) and `<body>` in place. Order: fetch, stage the stylesheets and EVALUATE the page's entry module before touching anything (the old page stays usable meanwhile), then in one synchronous task push the history entry, merge the head, swap the body and start the page (React mounts through `flushSync`, so there is no empty frame). Scroll is restored on back/forward. Any failure at any point falls back to `location.assign`, so the worst case is the old behaviour.
- **Pages cooperate through three small APIs.** React entries call `mountPage(import.meta.url, render)` (`src/lib/mountPage.tsx`): it mounts the first time and registers a `start` function for later swaps (unmounting through `window.vchShell.onLeave`). Page code never assigns `location.href` or calls `location.reload()`: it uses `navigateTo` / `refreshPage` (`src/lib/shellBridge.ts`). `useRadio` is only a binding to `window.vchShell.radio`. Static pages run one shared inline script that can run again after every swap (one-time listeners behind `window.__vchDd`, timers that stop when their node is detached, cleanup through `vchShell.onLeave`; `public/ai-widget.js` removes its `<style>` on leave).
- **Escape hatches.** `?softnav=off` (and `?softnav=on`, remembered in `localStorage.vch_softnav`) switches the swapping off in this browser; `data-vch-hard` on a link or `rel="external"` makes that link a normal navigation; the Vite dev server (`data-vch-dev`) never swaps. Pages that have no shell (reset-password, a stale static page from an old deploy) are left with normal navigation: the shell only swaps between pages it knows how to start.

## Consequences
- Music keeps playing through every section on desktop and phones with the one `<audio>` element; the first touch on a fresh document is still needed once (a typed URL, a reload, a link from another site, `reset-password.html`): that is the browser's autoplay policy and cannot be bypassed.
- A new React entry must use `mountPage` and must not navigate with `location.href`. A new static template must include `shellTag()` before any inline script that uses `window.vchShell`, and its inline script must be safe to run twice. `npm run verify:dist` fails when a built page misses the shell tag, references an outdated hash, loads the shell after the script that uses it, or carries its own copy of the radio.
- `scripts/e2e-shell.mjs` is the real-browser proof (Playwright + ffmpeg; not part of CI): it runs the built `dist/` in Chromium with `--autoplay-policy=document-user-activation-required`, once with a desktop and once with an iPhone profile, and checks one `<audio>` element, no pause, no new document and no new source across all sections, back/forward, track end, mute, fallbacks and the kill switch (which reproduces the old behaviour). Run it after any change to `src/shell/`, `mountPage`, the static page script or a new page type. It cannot replace one check on a real phone.
- Unit tests: `tests/shellNav.test.mjs` (navigation rules) and `tests/shellRadio.test.mjs` (the radio against a fake `<audio>` that follows the autoplay and load rules).
- A bug in the shell would hit every page, which is why it is small, has the fallbacks above and sits behind `?softnav=off`.

## Rejected
- *A single-page app (one HTML, client router).* Would remove the document change for good, but throws away the per-page static HTML that the SEO and the agent surface depend on and means rewriting every page.
- *An iframe or a popup player.* Fragile on phones, breaks the layout and the history.
- *Media Session / service worker tricks.* They do not keep an `<audio>` element alive across documents.
